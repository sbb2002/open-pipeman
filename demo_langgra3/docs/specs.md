# 프로젝트 명세: 비주얼 AI 파이프라인 빌더 (Visual AI Pipeline Builder)

## 1. 프로젝트 개요 (Overview)

본 프로젝트는 '확률적으로 동작하는 LLM을 결정론적인 워크플로우로 제어'하기 위한 **노드 기반 비주얼 프로그래밍 플랫폼**입니다. 사용자가 자연어로 로직을 기술하면 LLM이 실행 가능한 코드를 생성하고, 이를 데이터 흐름도(Dataflow Graph) 상에서 결합하여 하나의 완성된 애플리케이션(예: 인터랙티브 계산기, 비디오 텍스트 분석기 등)을 구축하는 것을 목표로 합니다.

**핵심 지향:** 기존 바이브 코딩은 LLM의 확률적 특성 때문에 결과물을 신뢰하기 어려웠습니다. 이 프로젝트는 코드의 제작 과정은 설명할 수 없더라도, **결과물 코드의 구성(I/O 규격, 실행 흐름)을 명시적으로 드러내어** 초보자부터 숙련자까지 모두 믿고 쓸 수 있는 바이브 코딩 환경을 지향합니다.

---

## 2. 프로젝트 목적 (Objectives)

* **추상화의 구체화:** 사용자의 모호한 의도를 명확한 I/O 규격(JSON Schema)을 가진 셀 구조로 변환.
* **신뢰성 확보:** LLM의 코드 생성 오류(Black-box error)를 잡아내기 위한 유닛 테스트 및 가드레일 시스템 내장.
* **상태 관리의 시각화:** 복잡한 에이전트의 상태(State) 변화를 캔버스 위에서 실시간으로 모니터링 및 디버깅.
* **모듈화된 재사용성:** 특정 기능을 수행하는 셀(Cell)을 부품화하여 다양한 파이프라인에 즉시 이식.

---

## 3. 사용자 워크플로우 (User Workflow)

### 기본 작업 순서
1. **셀 배치** — 캔버스 위에 필요한 셀을 추가 (좌하단 트레이 드래그 또는 캔버스 우클릭)
2. **프롬프트 작성** — 각 셀의 Inspector 패널에서 원하는 기능을 자연어로 기술
3. **셀 연결** — 데이터 흐름에 따라 셀을 연결 (직렬 또는 병렬)
4. **Run** — INPUT → ... → OUTPUT 경로가 완성되면 실행
5. **결과 확인** — 각 셀의 코드 생성 결과 및 실행 결과를 Inspector에서 확인
6. **Export** — 전체 파이프라인을 단일 파일(Python 스크립트 등)로 내보내기

### 최종 결과물
- 각 셀에서 생성된 코드를 연결 순서에 맞게 묶은 **단일 실행 파일**
- 데이터 관점에서 최초 INPUT에 대해 최종 OUTPUT을 반환하는 완결된 프로그램
- 플랫폼 내 실행(E2B 샌드박스)과 외부 다운로드 모두 지원 (현재는 export 우선)

---

## 4. 셀 타입 정의 (Cell Types)

### 4-1. INPUT 셀
- 파이프라인의 시작점. 반드시 1개 이상 존재.
- JSON Schema로 출력 타입을 선언 (예: `{ "file_path": "string", "width": "number" }`)
- 코드를 생성하지 않음. I/O 계약의 출발점 역할.

### 4-2. OUTPUT 셀
- 파이프라인의 종료점. 반드시 1개 이상 존재.
- JSON Schema로 입력 타입을 선언하여 최종 결과물의 형태를 규정.
- 코드를 생성하지 않음. I/O 계약의 도착점 역할.

### 4-3. 일반 셀 (Process Cell)
- 사용자가 자연어 프롬프트를 작성하면 LLM이 해당 기능을 수행하는 코드를 생성.
- 생성 언어 제한 없음 (Python, JavaScript, Bash 등).
- upstream 셀의 JSON Schema를 입력으로 받아, downstream으로 넘길 JSON Schema를 출력.
- Skill.md를 참조하여 코드 생성 컨벤션/제약 적용 가능.

### 4-4. 분기 셀 (Branch Cell) — 미구현
- 마름모(◇) 형태로 시각적으로 구분.
- 이전 셀의 output JSON에서 특정 필드의 타입/값에 따라 다음 셀로의 경로를 분기.
- 분기 조건 예시:
  ```
  output.type == "image"  →  셀 A
  output.type == "text"   →  셀 B
  ```
- 캔버스 우클릭 또는 좌하단 트레이에서 일반 셀과 동일한 방식으로 추가.
- Broadcasting(1:N 분사) 및 Aggregating(N:1 수집) 전략의 핵심 구성 요소.

---

## 5. 셀 간 데이터 계약 (I/O Contract)

### JSON Schema 기반 (언어 무관)
모든 셀 간 데이터 교환은 **JSON Schema**로 정의됩니다. 생성 코드가 Python이든 JavaScript든 관계없이, 셀 경계에서 주고받는 데이터는 항상 JSON 직렬화 가능한 값으로 제한됩니다.

**사용자 노출 인터페이스 (경량화):**
```
필드명        타입        필수여부
──────────────────────────────
image_path    string      ✓
width         number
height        number
metadata      object
```

**내부 처리:**
- JSON Schema로 직렬화하여 셀 간 유효성 검증에 사용
- LLM 코드 생성 시 스키마를 시스템 프롬프트에 포함 → 함수 시그니처 강제
- 분기 셀의 조건 정의에 재활용

**JSON으로 담기 어려운 데이터 (GPU 텐서, 바이너리 등):**
- 파일 경로(string) 참조 방식으로 우회

---

## 6. Skill.md 시스템

LLM이 코드를 생성할 때 참조하는 컨벤션/제약 문서입니다.

### 적용 단위
| 단위 | 설정 위치 | 적용 범위 |
|---|---|---|
| 셀 단위 | Inspector 패널 > Cell Config | 해당 셀에만 적용 |
| 프로젝트 단위 | Project Config 트레이 (미구현) | 프로젝트 내 모든 셀에 적용 |

### Project Config 트레이 (미구현)
- 캔버스 좌상단 툴 트레이와 **구분선으로 분리된** 별도 아이콘으로 배치
- 클릭 시 Skill.md 업로드/편집 패널 오픈
- 설정된 Skill.md는 모든 셀의 코드 생성 시 시스템 프롬프트에 자동 포함

---

## 7. 실행 환경 (Execution Environment)

### E2B 샌드박스
- 기본 제공 런타임: Python, JavaScript/TypeScript, R, Java, Bash
- 커스텀 템플릿으로 추가 런타임 설치 가능 (Ruby, C++ 등)
- Firecracker microVM 기반 하드웨어 격리
- **GPU 집약적 워크로드는 현재 지원 범위 밖** (추후 별도 검토)

---

## 8. 프론트엔드 지향점 (Frontend Philosophy)

프론트엔드는 단순한 UI를 넘어 '런타임 시뮬레이터'의 역할을 지향합니다.

* **직관적 선언 프로그래밍:** 사용자가 `if-else` 분기를 직접 그리는 대신, 분기 셀과 병렬 노드 배치로 로직을 구성.
* **실시간 상태 추적 (Visual Tracing):** 데이터가 노드 사이의 엣지(Edge)를 흐르는 모습을 시각화하고, 각 단계의 스냅샷(이미지, 텍스트, JSON)을 즉각 확인. — **미구현**
* **하이브리드 인터페이스:** 전문가를 위한 상세 설정 패널(모델 파라미터, 시스템 프롬프트)과 일반인을 위한 단순화된 위젯(버튼, 입력창) 모드를 동시에 제공. — **미구현**

---

## 9. 백엔드 지향점 (Backend Philosophy)

백엔드는 '안정적인 실행 엔진'과 '엄격한 검증자'의 역할을 지향합니다.

* **LangGraph 기반 상태 제어:** Cyclic 구조를 배제한 DAG(Directed Acyclic Graph)를 기본으로 하되, Checkpointer를 통한 상태 보존 및 Human-in-the-loop(일시정지 및 개입) 지원.
* **엄격한 I/O 컨트랙트:** 모든 셀은 실행 전 입력 데이터의 JSON Schema 유효성을 검사하며, LLM 응답을 JSON 모드 및 후처리 스니펫(Sanitizer)으로 정제하여 데이터 오염 방지.
* **자동 검증 시스템 (Auto-Validator):** 사용자가 정의한 샘플 I/O를 바탕으로, LLM이 생성한 코드가 의도대로 작동하는지 런타임 직전에 단위 테스트 수행.
* **동적 코드 실행 환경:** 생성된 코드를 E2B 샌드박스에서 격리 실행하고 결과를 파이프라인으로 반환.

---

## 10. 핵심 데이터 흐름 규칙 (Protocol)

1. **Strict Direction:** 모든 흐름은 `INPUT`에서 시작하여 `OUTPUT`으로 종료되며, 역방향 흐름은 금지됨.
2. **Schema-First:** 셀 간 연결 시 JSON Schema의 타입(Type)과 키(Key) 일치 여부를 최우선으로 검증.
3. **Parallel Intelligence:** 하나의 입력을 여러 셀로 분사(Broadcasting)하고, 결과를 통합(Aggregating)할 때 조건에 맞는 결과만 선택. 분기 셀이 이 전략의 핵심 구성 요소.

### [LLM을 위한 요약 가이드]

> "이 시스템은 사용자가 '말'로 만드는 프로그램을 '구조'로 고정하는 장치다. 너는 각 셀의 I/O를 JSON Schema로 명확히 정의하고, 이전 셀에서 넘어온 스키마를 깨지 않도록 코드를 생성해야 한다. 생성 언어는 Python에 국한되지 않으나, 셀 경계의 데이터는 반드시 JSON 직렬화 가능해야 한다. LLM 특유의 사족을 배제하고 오직 규격화된 데이터만을 반환하는 '순수 함수적 셀'을 만드는 데 집중하라."
