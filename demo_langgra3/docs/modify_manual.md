# 코드 수정 출력 지침 (Patch Mode)
* 코드 수정을 요청받으면 'structure.md'를 참고하여 어떤 파일을 수정할지 선택하여 사용자에게 요청하시오.
* 사용자가 요청한 파일을 전달해주면 해당 파일을 모두 읽고 수정 작업을 시작하시오.
* 수정하여 추가될 새 기능, 디자인, 코드가 수정하지 않는 기존 기능, 디자인, 코드와 충돌할 우려가 있는지 검사하시오. 
* 만약 충돌할 우려가 있다면 미리 사용자에게 알리고 충돌하지 않을 방법을 제안한 후 사용자의 재확인을 받아 수정작업을 진행하시오.
* 모든 수정 사항은 아래 JSON 양식으로만 작성하십시오. (설명 생략, JSON만 출력)
    * **라인 번호 기준:** 1-based index를 사용하며, 빈 줄과 주석을 포함한 실제 파일의 라인 번호를 정확히 파악하십시오.
    * **패치 전 파일 확인 필수:** JSON 출력 전에 반드시 현재 파일의 실제 내용과 줄 번호를 직접 확인하십시오. 이전 대화의 기억에만 의존하지 마십시오.
    * **무결성 유지:** 같은 파일 내 여러 지점 수정 시 (from, to) 범위가 겹치지 않게 하십시오. 겹치는 구간은 하나의 'target' 객체로 합쳐서 작성하십시오. 범위가 겹치면 patch_applier.py가 에러를 출력하고 적용을 중단합니다.
    * **들여쓰기:** `replace` 내의 코드는 해당 파일의 기존 들여쓰기 규칙을 엄격히 준수하십시오.
    * **교체 범위 산정:** `replace` 내용의 줄 수가 교체 대상(from~to) 줄 수보다 많거나 적어도 정확히 동작합니다. 단, 교체 후 주변 코드와 문법적으로 올바르게 이어지는지 반드시 확인하십시오.
        * **`to` 줄 번호는 반드시 파일을 직접 열어 눈으로 확인하십시오.** 교체할 블록의 실제 마지막 줄(`}`, `);` 등)을 파일에서 찾아 `to`에 기입하십시오. 추정하거나 계산으로 산출하지 마십시오. `to`가 짧으면 원본 잔재 코드가 새 코드 뒤에 붙어 문법 오류가 발생합니다.
        * **`replace` 문자열 안에 백틱(`` ` ``)과 중첩 템플릿 리터럴을 사용하지 마십시오.** JSON 직렬화 과정에서 파싱 오류가 발생합니다. HTML/JS를 동적으로 생성하는 코드를 작성할 때는 `innerHTML` 대신 DOM API(`createElement`, `setAttribute` 등)를 사용하십시오.
    * **삭제:** `replace: ""`를 사용하십시오.
    * **삽입:** `from`과 `to`를 동일한 줄 번호로 지정하십시오. 기존 줄은 보존되며, 해당 줄 번호 **앞**에 코드가 삽입됩니다.
    * **파일 전체 교체:** 파일 구조가 크게 손상되었거나 변경량이 50줄을 초과하는 경우, 부분 패치 대신 `from: 1, to: (파일 전체 줄 수)`로 전체를 교체하십시오. 이 방법이 줄 번호 오계산 위험이 없어 더 안전합니다.
* 수정 완료 후 아래와 같이 체크하시오.
    - 수정된 기능 및 디자인: 모두 반영
    - 수정하지 않은 원본 기능 및 디자인: 유지
    - index.html을 열었을 때 잘 작동해야 함.
* 만약 사용자가 추가 수정을 요구할 경우에는 최근 수정한 파일을 기준으로 수정 작업을 진행하시오.

## ⛔ 패치 출력 전 필수 체크리스트 (생략 불가 — 위반 시 JSON 출력 금지)

아래 3가지를 모두 확인하지 않으면 JSON을 출력하지 말 것. 확인 절차를 건너뛰는 것은 잔재 코드, 문법 오류, 줄 번호 drift를 유발하며 이번 세션에서 반복적으로 발생한 근본 원인이다.

1. **줄 번호 기준 확인 — patch_applier 리포트 우선**
   - 이 파일에 대해 patch_applier.py가 출력한 **"다음 패치 기준" 섹션**이 있는가?
     - **있다면:** 그 섹션의 줄 번호와 컨텍스트를 유일한 기준으로 삼을 것. 이전 view 결과와 패치 전 기억은 완전히 폐기할 것.
     - **없다면(첫 패치이거나 리포트를 받지 못한 경우):** `view` 도구로 `from` 줄과 `to` 줄을 JSON 출력 직전에 직접 열어 실제 텍스트를 눈으로 확인할 것. 기억에서 앵커를 쓰는 것은 절대 금지.

2. **이 파일의 누적 패치 횟수 확인**
   - 이번 세션에서 이 파일에 몇 번 패치했는가?
   - **3회 이상이고 리포트가 없는 경우:** 줄 번호 drift 위험. 반드시 사용자에게 파일 재업로드를 요청한 뒤 진행할 것.
   - **3회 이상이더라도 patch_applier 리포트의 "다음 패치 기준"이 있는 경우:** 리포트를 기준으로 진행 가능. 단, 리포트가 가장 최신 패치의 것인지 반드시 확인할 것.
   - **재업로드 없이, 리포트도 없이 계속 진행하는 것은 금지.**

3. **delta 계산 완료 여부**
   - 같은 JSON 안에 여러 target이 있을 경우, 위→아래 순서로 각 target의 delta를 계산하고 다음 target의 from/to에 누적 반영했는가?
   - delta = (replace의 실제 줄 수) − (to − from + 1)
   - 계산하지 않았다면 → 계산 후 진행할 것.

### 패치 대신 bash_tool로 직접 파일 생성이 강제되는 경우

아래 중 하나라도 해당하면 패치 JSON 대신 `bash_tool`로 파일을 직접 수정/생성할 것:
- 같은 파일에 누적 패치 **3회 초과**이고, 리포트도 없고, 재업로드도 없는 경우
- 이전 패치 적용 결과를 리포트 또는 `view`로 확인하지 못한 상태
- delta 계산 결과가 불확실한 경우
- 앵커 오류(미발견·중복)가 **2회 연속** 발생한 경우

## 패치 적용 후 리포트 활용 규칙 (Post-Patch Report) ⭐

patch_applier.py v3부터 패치 성공 시 아래 형식의 리포트가 출력된다.
이 리포트는 **Claude가 v1 기억 대신 현재 파일 상태를 정확히 파악하기 위한 유일한 근거**다.

```
── 다음 패치 기준 (새 줄 번호 기준 전후 컨텍스트) ──
  [target 1 전후 컨텍스트]
  L  38: ...
  L  39: ...  ← 변경 시작
  L  40: ...
  L  41: ...  ← 변경 끝
  L  42: ...
```

### 리포트 활용 절차

1. **패치 성공 후** 사용자가 리포트를 붙여넣으면, 해당 파일의 이전 view 결과와 기억을 즉시 폐기하고 리포트의 내용으로 대체하시오.
2. **다음 패치 작성 시** `from` / `to` / `anchor_start` / `anchor_end`는 리포트의 "다음 패치 기준" 섹션에 표시된 줄 번호와 텍스트를 기준으로 작성하시오.
3. **앵커 자동 보정 활용:** patch_applier.py v3는 앵커가 ±10줄 범위 내에서 발견되면 줄 번호를 자동 보정하고 보정량을 리포트에 표시한다. 보정이 발생한 경우, 다음 패치에서는 보정된 실제 줄 번호를 기준으로 작성하시오.
4. **리포트가 없는 경우(오류 발생 또는 사용자가 붙여넣지 않은 경우):** view 도구로 현재 파일을 직접 열어 재확인할 것.

## 줄 번호 추적 규칙 (Line Offset Tracking)
* **패치를 생성할 때마다** 해당 target이 파일에 적용된 후 줄 번호가 얼마나 밀리는지 계산하고, 이후 target의 from/to에 반영하시오.
    * delta = (replace의 실제 줄 수) − (to − from + 1)
    * 삽입(from == to)의 경우 delta = replace의 실제 줄 수
    * 삭제(replace == "")의 경우 delta = −(to − from + 1)
* **같은 JSON 안에 여러 target이 있을 경우**, 위→아래 순서로 각 target의 delta를 누적하여 다음 target의 from/to에 더하시오.
    * patch_applier는 역순으로 적용하므로, JSON 작성은 원본 줄 번호 기준으로 위→아래 순서로 누적할 것.
    * 예시: target A(from=10, to=12, replace 5줄) → delta=+2 → target B의 from/to에 +2 적용
* **패치가 여러 번 누적된 경우(대화가 길어진 경우)**, patch_applier 리포트의 누적 delta와 파일 현황을 참고하여 현재 줄 번호를 파악하시오. 리포트가 없으면 파일을 직접 열어 재확인하시오.
* **재업로드 강제:** 같은 파일에 패치가 **3회 이상** 누적되고 리포트도 없는 경우, 줄 번호 오산 위험이 커집니다. 반드시 사용자에게 파일 재업로드를 요청하고, 재업로드 전까지 해당 파일의 패치 JSON 출력을 중단하시오.

## 앵커 검증 규칙 (Anchor Verification)
* 모든 target에 `anchor_start`와 `anchor_end` 필드를 **반드시** 포함하시오.
    * `anchor_start`: from 줄의 실제 내용에서 **들여쓰기 포함 앞 30글자** (파일 또는 리포트를 직접 열어 복사)
    * `anchor_end`: to 줄의 실제 내용에서 **들여쓰기 포함 앞 30글자** (파일 또는 리포트를 직접 열어 복사)
* **앵커 출처 우선순위:**
    1. patch_applier 리포트의 "다음 패치 기준" 섹션에 표시된 텍스트 → 최우선 사용
    2. 리포트가 없는 경우 → view 도구로 파일을 직접 열어 복사
    3. 기억이나 추론으로 작성하는 것 → **절대 금지**
* **⛔ 앵커 추정 절대 금지 (반복 실수 방지):** `anchor_start`와 `anchor_end`는 절대 기억이나 추론으로 작성하지 마십시오. 반드시 리포트 또는 view 도구로 해당 줄의 실제 텍스트를 눈으로 확인하고 복사하십시오.
    * **from과 anchor_start는 항상 같은 줄을 가리켜야 합니다.** `from: 730`이면 `anchor_start`는 730번 줄의 텍스트여야 하며, 730번 줄 근처의 다른 줄(예: 727번 주석)을 쓰면 앵커 불일치 에러가 발생합니다.
* 삽입(from == to)의 경우 `anchor_start`만 기입하고, `anchor_end`는 생략해도 됩니다.
* patch_applier.py v3는 from/to 기준 ±10줄 범위 내에서 앵커를 탐색하며, 발견된 위치가 JSON과 다르면 **자동 보정 후 적용**합니다. 리포트에 보정량이 표시됩니다.
    * **미발견:** 줄 번호가 ±10줄을 초과하여 밀렸을 가능성. **즉시 파일 재업로드를 요청하고 재업로드 전까지 해당 파일 패치를 중단할 것.**
    * **중복:** 앵커 문자열이 범위 내 여러 줄에 존재. 앵커를 더 길게(30글자 이상) 지정하십시오.
    * **앵커 오류가 2회 연속 발생한 경우:** 패치 방식을 포기하고 bash_tool로 파일을 직접 수정할 것.

## 버전 관리 규칙 (Version Tracking)
* 사용자가 이번 세션에서 **최초로 업로드한 파일은 자동으로 v1**으로 간주한다.
* JSON을 출력할 때마다 해당 파일의 **현재 버전**을 `"version"` 필드에 반드시 명시하시오.
* 패치가 적용될 때마다 해당 파일의 버전은 **+1** 증가한다. Claude는 대화 컨텍스트를 기반으로 각 파일의 현재 버전을 추적하시오.
* 사용자가 파일을 **재업로드**하면 해당 파일의 버전을 **v1로 리셋**하여 다시 계산하시오.
* 버전이 불확실한 경우 JSON 출력 전에 사용자에게 현재 버전을 확인하시오.
* `"version"` 필드는 정보 표시 목적이며, patch_applier.py는 이를 로그로만 출력하고 적용을 차단하지 않는다.
* **패치 횟수 고지:** JSON을 출력할 때마다 해당 파일이 이번 세션에서 몇 번째 패치인지 사용자에게 명시할 것. 예: "inspector.js v3 — 이번 세션 3번째 패치". 리포트가 없는 상태로 3회 도달 시 재업로드 요청과 함께 출력할 것.

## patch_applier.py 동작 규칙 (참고 — v3 기준)
* **교체:** `replace` 문자열을 줄 단위로 분리하여 `from~to` 구간과 정확히 교체합니다. 교체 내용의 줄 수가 달라도 올바르게 처리됩니다.
* **삽입 (`from == to`):** 기존 줄을 덮어쓰지 않고, 해당 줄 앞에 삽입합니다.
* **삭제 (`replace: ""`):** 해당 구간을 완전히 제거합니다.
* **앵커 자동 보정:** `anchor_start` / `anchor_end` 필드가 있으면, from/to 기준 ±10줄 범위 내에서 탐색합니다. 발견된 위치가 JSON과 다르면 자동 보정하여 적용하고 보정량을 리포트에 출력합니다. 미발견·중복 시 적용을 중단합니다.
* **적용 후 리포트 출력:** 성공 시 변경 구간 정보, 파일 현황(수정 전후 줄 수, 누적 delta), 다음 패치 기준 컨텍스트(변경 구간 전후 3줄)를 출력합니다.
* **에러 시 중단:** 아래 경우 해당 파일의 패치를 중단합니다.
    * `from > to`
    * 범위가 파일 총 줄 수를 초과
    * 같은 파일 내 target 범위끼리 중복
    * 앵커 미발견 / 앵커 중복

[JSON Format]
```json
[
    {
        "file": "경로/파일명.확장자",
        "version": N,
        "target": [
            {
                "from": 시작_라인_번호,
                "to": 끝_라인_번호,
                "anchor_start": "from줄의 indent+앞30글자",
                "anchor_end": "to줄의 indent+앞30글자",
                "replace": "수정/교체될 코드 내용"
            }
        ]
    }
]
```
