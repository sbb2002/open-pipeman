## 2. 반복된 근본 원인 패턴

| 패턴 | 발생 횟수 | 설명 |
|------|----------|------|
| **앵커 추정** | 5회 | `view` 도구로 재확인하지 않고 기억에서 앵커를 작성하여 중복·불일치 발생 |
| **삽입 vs 교체 혼동** | 2회 | `from==to` 삽입 방식이 기존 줄을 보존한다는 점을 간과하여 잔재 코드 누적 |
| **delta 미추적** | 4회 | 이전 패치의 줄 수 변화를 계산하지 않아 이후 패치의 from/to가 밀림 |
| **재업로드 미요청** | 전반 | 3회 이상 패치 누적 시 재업로드를 요청해야 함에도 기억 기반으로 계속 진행 |
| **증상만 수정** | 3회 | 앵커 오류 발생 시 근본 원인(줄 번호 drift) 대신 앵커 텍스트만 수정하여 동일 문제 반복 |
| **패치 적용 결과 미확인** | 전반 | 패치 적용 후 `view`로 결과를 확인하지 않고 다음 패치를 출력하여 잔재 누적 |

## 3. 토큰 낭비 추정

| 구분 | 내용 |
|------|------|
| **이론적 절감률** | 패치 1회 성공 시 전체 교체 대비 약 70~90% 절감 |
| **실제 결과** | 오류 15건 × (오류 분석 + view 재확인 + 재출력) 사이클 반복으로 전체 교체 대비 토큰을 오히려 더 소비했을 가능성 높음 |
| **결론** | 패치 방식의 절감 효과는 **한 번에 성공할 때만 실현**됨. 실패가 반복되는 순간 역효과 발생 |
